# BearVault Project Guide

This document is the beginner-friendly map of BearVault. Start here when you need to understand where a page lives, what a folder is responsible for, or which file should be changed.

## The five-minute explanation

BearVault has two versions of the finance interface:

1. The signed-in application uses real household records. Its pages live under `app/(app)/`.
2. The public demo uses safe example records. Its pages live under `app/demo/`.

Both versions reuse feature interfaces from `components/`. Real data is loaded through `lib/data/` and stored in Supabase. Demo data comes from mock files in `lib/` and stays out of the production database.

```text
Browser URL
   |
   v
app/.../page.tsx             Selects the page and loads its starting data
   |
   v
components/...Workspace.tsx  Displays the page and handles interaction
   |
   v
lib/data/...ts               Reads validated household data
   |
   v
Supabase                     Stores real financial records
```

Files ending in `.module.css` style the component with the same name. For example, `AccountsWorkspace.module.css` styles `AccountsWorkspace.tsx`.

| Budgets | `app/(app)/budget/page.tsx` | `app/demo/budget/page.tsx` | `components/budget/BudgetWorkspace.tsx` | Plans category amounts and records spending against the monthly budget. |

Parentheses in `(app)` are a Next.js route group. They organize code but do not appear in the URL. Brackets such as `[[...sign-in]]` describe a flexible URL handled by Clerk.

## Root folders

| Folder | What it contains | Should a beginner edit it? |
| --- | --- | --- |

| `.clerk/` | Local files generated by Clerk tooling. | No, unless Clerk documentation explicitly asks for a change. |
| `.git/` | Git history and repository internals. | Never edit manually. |
| `.next/` | Generated Next.js development and build output. | Never edit. It is recreated automatically. |
| `app/` | URLs, layouts, API routes, page entry points and global CSS. | Yes. Start here when adding or locating a page. |
| `components/` | Reusable visual interfaces and feature workspaces. | Yes. Most UI work happens here. |
| `idea/` | Earlier page-layout reference images. | Reference only. It is not loaded by the application. |
| `lib/` | Data access, Supabase connections, mock data, domain types and shared helpers. | Yes, when changing data behavior or shared calculations. |
| `new design/` | The newest supplied design screenshots. | Reference only. It is intentionally not part of application code. |
| `node_modules/` | Installed third-party packages. | Never edit. Use `package.json` and npm instead. |
| `Photos/` | Brand and visual reference images. | Reference only unless an application file deliberately imports one. |
| `supabase/` | Versioned SQL migrations that define the database. | Only when intentionally changing the database schema or security policies. |
| `types/` | TypeScript declarations for packages that need extra type information. | Occasionally. |

## The `app/` folder

The `app/` folder defines the URLs users can visit.

| Path | Responsibility |
| --- | --- |
| `app/layout.tsx` | Root HTML document. Loads Clerk, Mantine, global preferences, Manrope, metadata and mobile viewport support. |
| `app/globals.css` | Global design tokens, theme colors, palette variables, density rules and shared browser defaults. |
| `app/page.tsx` | Public marketing/landing page at `/`. |
| `app/page.module.css` | Landing-page styling. |
| `app/(app)/` | All authenticated finance pages. |
| `app/(app)/layout.tsx` | Security gate for protected pages. Requires a Clerk user and household organization, then renders `AppShell`. |
| `app/(app)/loading.tsx` | Loading state shared by protected pages. |
| `app/(app)/error.tsx` | Error boundary shared by protected pages. |
| `app/demo/` | Public, interactive versions of the finance pages using example data. |
| `app/demo/layout.tsx` | Wraps every demo page in `DemoShell`. |
| `app/api/` | Server endpoints called by the interface. Currently contains the market-data endpoint. |
| `app/onboarding/` | Household creation/joining flow. |
| `app/sign-in/` and `app/sign-up/` | Clerk authentication screens. |
| `app/icon.tsx`, `app/apple-icon.tsx`, `app/favicon.ico` | Browser and installed-app icons. |
| `app/manifest.ts` | Progressive-web-app metadata. |
| `app/auth.module.css` | Shared authentication-page styling. |

Inside a feature route:

- `page.tsx` is the page entry point.
- `actions.ts` contains server-side create, update or delete operations.
- A nearby `.module.css` file styles a route only when the styling is route-specific.

## The `supabase/` folder

Database changes are stored as ordered SQL migrations. Never change an already-deployed migration just to alter production data. Add a new migration for a new schema change.

| Migration | Purpose |
| --- | --- |
| `20260811000100_create_household_finance_schema.sql` | Creates the original household, budget, income and investment schema with household isolation. |
| `20260812000100_create_savings_goals.sql` | Adds savings goals. |
| `20260814000100_create_financial_accounts.sql` | Adds cash, credit and other financial accounts. |
| `20260814000200_link_budget_entries_to_accounts.sql` | Connects budget entries to financial accounts. |

## How real and demo data stay separate

### Signed-in application

```text
Clerk user and organization
  -> protected app layout
  -> server page
  -> lib/data repository
  -> authenticated Supabase client
  -> row-level security
```

### Public demo

```text
Public /demo URL
  -> demo page
  -> mock data from lib/
  -> the same feature workspace in demo mode
  -> local React state only
```

Demo mode must not call production create/update/delete actions. It should also avoid protected APIs when a local visual substitute is available.

## How the UI is assembled

### Desktop

```text
AppShell or DemoShell
├── 248px sidebar
│   ├── BearVault brand
│   ├── main navigation
│   ├── account summary rail
│   └── household/user footer
└── content column
    ├── 48px page header
    └── page workspace
```

### Mobile

```text
Compact page header
Scrollable page workspace
Fixed bottom navigation
└── More drawer for secondary destinations
```

The feature CSS Modules contain page-specific responsive rules. The main mobile breakpoint is approximately `48rem`. Dense desktop tables hide less-important columns or become stacked rows on small screens. Detail panels become drawers or bottom sheets when necessary.

## Theme and palette flow

```text
SettingsWorkspace
  -> PreferencesProvider
  -> localStorage
  -> data-theme / data-palette / data-density / data-motion
  -> CSS variables in app/globals.css
  -> every CSS Module
```

Use `lib/themePalettes.ts` when adding or changing a palette. Use `components/settings/PaletteDropdown.tsx` when changing the palette-selection interface. Use `app/globals.css` for shared theme tokens, not for one page's private layout.

## Where should I make a change?

| Goal | Start here |
| --- | --- |
| Rename a navigation page | `components/layout/navigation.ts`, then check `components/demo/DemoShell.tsx`. |
| Change the sidebar or mobile navigation | `components/layout/` and `components/demo/DemoShell.tsx`. |
| Change colors everywhere | `app/globals.css` and `lib/themePalettes.ts`. |
| Change only one page's layout | That feature's `Workspace.tsx` and matching `.module.css`. |
| Change dashboard calculations | `components/dashboard/dashboardViewModel.ts`. |
| Change database reading | The matching file in `lib/data/`. |
| Add a create/update/delete operation | The feature route's `actions.ts`, then call it from the workspace. |
| Change investment calculations | `lib/investmentData.ts`. |
| Change demo records | `lib/mockFinanceData.ts`, `lib/accounts.ts`, or `lib/investmentData.ts`. |
| Add a database field/table | Add a new file under `supabase/migrations/`, then update types, data access and UI. |
| Add a reusable UI primitive | `components/ui/`. |
| Update app icons or metadata | `app/icon.tsx`, `app/apple-icon.tsx`, `app/manifest.ts`, or `app/layout.tsx`. |

## Safe beginner workflow

1. Find the browser page in the page map.
2. Open its `page.tsx` to see what data it loads.
3. Follow the imported `Workspace` component to see the interface.
4. Open the matching `.module.css` file for its appearance.
5. Follow imports into `lib/data/` only if the data itself needs to change.
6. Run `npm run lint` and `npm run build` before committing.

Do not edit `.next/`, `node_modules/`, `.git/`, or an old deployed Supabase migration.
